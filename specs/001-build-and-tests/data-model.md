# Data Model: test artefacts (001)

This feature adds no application data and does not change the `.dat` formats
(see `docs/architecture.md`). The entities below are the test artefacts committed under
`src/dealerdesk/tests/`. The file layout is in
[contracts/scenario-format.md](contracts/scenario-format.md).

## Terminology

These names are used across spec, plan, contracts and tasks, and each pair means the
same thing:

- **golden output** = a scenario's `expected.out` file (spec "Golden output")
- **golden data** (also "golden copy" or "data goldens") = a scenario's `expected-data/` directory
- **goldens** = both of the above, written only by `make golden`

## Scenario (e2e)

| Field | Form | Rules |
|-------|------|-------|
| id | directory name `NN-<kebab-name>` | unique, two-digit prefix sets the run order |
| input | file `input` | keystrokes, one line per prompt answer, LF endings; normally ends by leaving every menu with `0` |
| expected output | file `expected.out` | normalised stdout (see Normalisation rule); must exist |
| fixture | optional file `fixture`, one word | `sample` (default, the repo `data/`), `empty`, `full` |
| expected data | optional directory `expected-data/` | all `.dat` files after the run, normalised; if absent, the data must equal the fixture |
| covers | row in the `tests/README.md` coverage table (not inside the scenario files) | each `BR-` item appears at least once (SC-003) |

Lifecycle: created with `make golden` from the `a2ba708` code, then reviewed and
committed. After that it is read-only, and it changes only when a spec approves a
behaviour change (for example 002 adding the fleet field). The diff is reviewed in the
same change.

## Fixture

| Name | Content | Purpose |
|------|---------|---------|
| `sample` | the committed `data/` (12 vehicles, 8 customers, 3 invoices, counters 1013/2009/50233) | default for all scenarios |
| `empty` | no `.dat` files | BR-070 missing file → empty table, default counters 1000/2000/50000 |
| `full` | generated by `fixtures/make-full.sh`: 500 vehicles, 500 customers, 2000 invoices | BR-081 "file is full!" messages |

A fixture is always copied into a temporary directory and is never modified in place.

## Normalisation rule

Applied in this order to the output and to the data files before comparing (research R-5):

1. remove `\033[2J\033[H`
2. `DEALERDESK v<major>.<minor>` → `DEALERDESK vX.Y`
3. the run date(s) `YYYY-MM-DD` captured before and after the run → `<TODAY>`

No other rewriting. Whitespace, trailing blanks and money formatting are compared exactly.

## Unit case (pricing)

| Field | Type | Notes |
|-------|------|-------|
| name | string | for example `"inv50231 trade 0%"` |
| list, disc_pct, tradein | double | inputs |
| cust_type | char | `'R'` or `'T'` (any other char behaves as R; one case pins this) |
| expected | 10 strings | `%.2f` of list, trade_disc, disc_pct, disc, net, delivery, vat, reg_fee, tradein, total |

A case passes when every formatted field matches. `rnd2` has its own small table of
(input, expected `%.2f`) pairs at half-penny boundaries.

## Relationships

- A scenario uses 0 or 1 fixture (default `sample`). Its expected data equals the fixture
  plus the scenario's writes.
- The coverage table maps `BR-` items to scenarios and unit cases (plan.md "Coverage map").
